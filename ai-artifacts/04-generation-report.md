Ни одно обязательное Product Readiness Requirement не отсутствует. Ниже перечислены пробелы, которые не блокируют готовность модели продукта, но требуют закрытия на последующих этапах:

- Точные идентификаторы полей/событий в системе Set для показателей из `entities-and-data-dictionary.md` (маппинг схемы данных).
- Полнота перечня технических причин недоступности — исходная страница Confluence 5715099678 находится вне дерева требований и не была загружена.
- Статус и приоритет ИИ-консультанта и проактивного сценария (LFL-прогноз) в дорожной карте — подтверждено, что это надстройка вне MVP1/MVP2, но конкретный релиз не определен (демо-версия отдельно подтверждена для визуального прототипа, см. `requirements/02-system/ai-advisor-concept.md`).
- Расшифровка аббревиатуры «ЦСЛ» и протокол интеграции (формат обмена, SLA).
- Механизмы аутентификации/авторизации и retry-политики для всех интеграций (касса → Kafka, DWH → ЦСЛ, Superset → Set Centrum).
- Точная периодичность оплаты подписки (ежемесячно/ежегодно) — тип объекта продажи, принцип цены и факт подписки подтверждены, конкретный интервал не уточнялся.
- Технический риск: возможность дублирования/потери чеков при смене master-кассы — требует проверки у архитекторов Set Retail, не у Product Manager.
- Точный подход к логированию платформы (конкретный лог-агрегатор Set Retail и способ подключения) — требует проверки у архитектора.
- Детальные характеристики серверного оборудования (CPU/RAM/диски) под каждый профиль сети — сайзинг по магазинам/кассам подтвержден, инженерный расчет ресурсов не выполнен (ожидаемо, задача следующего этапа — архитектуры).

## Уточнения объема, внесенные на этапе модели экранов (2026-07-21)

Следующие решения Product Manager были приняты уже после утверждения статуса `READY_FOR_SCREEN_MODEL`, при разборе отчета `ai-artifacts/05-screen-model-report.md`, и обратно внесены в `requirements/` и в эту модель для консистентности:

- **Постановка задач и контроль выполнения — MVP2, не MVP1.** Ранее сущность «Задача», экран SCR-09 и связанные функции ролей не имели явной MVP-принадлежности. Теперь явно зафиксировано как MVP2 (см. `requirements/01-base/product-context.md`).
- **Маршрут эскалации задачи** — закрыт: цепочка РД → ОД.
- **Экран SCR-10 объединен с SCR-06** — детальный технический отчет о причинах недоступности общий для всех ролей внутри «Дашборда доступности», не отдельный экран для «технических служб».
- **Объем доступа службы поддержки** — уточнен: включает коммерческие метрики (выручка, доля SCO), в отличие от «технических служб».
- **SCR-13 (ИИ-консультант)** — включен в визуальный прототип (демо на примере вопроса из Confluence); статус в общей продуктовой дорожной карте остается отдельным открытым вопросом (см. ниже).

Дополнительно, при разборе бизнес-правил (2026-07-21), Product Manager внес пять содержательных исправлений:

- **Работа в офлайн-режиме.** Касса, временно потерявшая связь с сервером, но продолжающая функционировать, теперь явно считается **доступной** (не недоступной) — при условии локального накопления данных и их полной передачи без потерь при восстановлении связи. Это меняет формулировку условий доступности в `requirements/02-system/user-roles-and-functional-blocks.md` и `requirements/06-system-scenarios/system-scenarios.md`, и добавляет техническое требование к буферизации/синхронизации в `requirements/03-architecture/technical-constraints.md`.
- **Исправлена формула «Доступность SCO».** В `requirements/02-system/business-rules-and-formulas.md` формула для суточных агрегатов ошибочно указывала «длительность доступности / длительность в чеке» (внутренняя нестыковка исходных документов Confluence) — исправлено на корректную формулу «время доступности для покупки / время работы магазина», уже использовавшуюся в остальных разделах.
- **Пороги утилизации POS/SCO переведены из фиксированных значений в настраиваемый параметр**, выносимый в отдельное приложение настроек (вместе с нормативами p95/median) — не часть логики самих дашбордов.
- **Формализована функциональность «Постановка задач и контроль выполнения» (MVP2)** отдельным файлом `requirements/02-system/task-management.md` — ранее она была только implied через сценарии, без описания в основных функциональных требованиях.
- **Устранена неоднозначность ролей** в сценарии «Оптимизация нагрузки и ресурсов» (`requirements/07-scenarios/business-scenarios.md`) — ранее «директор» использовался без уточнения ОД/РД.

Эти правки не меняют статус `READY_FOR_SCREEN_MODEL` и не вводят новых блокеров, но уточняют содержание модели — см. обновленный `ai-artifacts/05-screen-model-report.md`.
