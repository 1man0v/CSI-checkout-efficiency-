## Реализованные сценарии

Прототип воспроизводит все ключевые сценарии из `requirements/07-scenarios/business-scenarios.md` и `requirements/02-system/task-management.md` **функционально**, а не только визуально — с сохранением и чтением данных из реальной БД:

1. **Верхнеуровневый мониторинг → поиск аутсайдеров → карточка магазина.** Дашборд сети агрегирует реальные данные из SQLite по ролевому масштабу (ОД — вся сеть, РД — регион «Москва-Восток»), список аутсайдеров фильтруется/сортируется на реальных данных, карточка магазина №404 воспроизводит документированный кейс (SCO №4, утилизация 2%).
2. **Постановка и выполнение задачи (MVP2).** Создание задачи с серверной валидацией обязательного поля, статусы Новая → В работе → Выполнено через кнопку и через drag-and-drop, эскалация по цепочке РД → ОД — все операции меняют состояние в таблице `tasks` и переживают перезагрузку страницы.
3. **Настройка нормативов и порогов (SCR-08, отдельное приложение) с согласованием РД → ОД.** Полный цикл проверен: РД пытается занизить норматив региона ниже сетевого → создается запись в `settings_approval_requests` → ОД видит очередь согласования и подтверждает → значение применяется в `settings_regional` и немедленно отражается в эффективных настройках региона.
4. **Технические причины простоя и заявка в ИТ (объединенный SCR-06).** Список причин, включая уточнение по офлайн-режиму («Нет связи» не равно недоступности), и создание заявки в ИТ, сохраняемой в таблице `it_tickets`.
5. **Диалог с ИИ-консультантом (демо).** Пример вопроса из `requirements/02-system/ai-advisor-concept.md` обрабатывается реальным API-эндпоинтом (`GET /api/advisor`), возвращающим сценарный структурированный ответ.
6. **Диагностика и аналитика продукта** (SCR-11, SCR-12) — данные читаются из тех же таблиц `registers`/`usage_stats`, коммерческие метрики (выручка) видны в диагностике, как подтверждено Product Manager.

## Реализованная модель данных, API и поведение бэкенда

**Стек:** Node.js (`node:http`, `node:sqlite` — без внешних зависимостей, без `npm install`), статическая раздача фронтенда тем же сервером. Обоснование выбора и ограничения — см. «Упрощения» ниже.

**Схема БД** (`prototype/backend/schema.sql`): `stores`, `registers`, `technical_causes`, `it_tickets`, `settings_network`, `settings_regional`, `settings_approval_requests`, `tasks`, `usage_stats`.

**API** (REST, JSON, `prototype/backend/routes/`):

| Метод и путь | Назначение |
| --- | --- |
| `GET /api/stores`, `GET /api/stores/:id` | Список/детали магазинов с вычисленной классификацией аутсайдера |
| `GET /api/technical-causes`, `GET/POST /api/tickets` | Причины простоя, заявки в ИТ |
| `GET/PUT /api/settings`, `GET /api/settings/approvals`, `POST /api/settings/approvals/:id` | Нормативы/пороги и очередь согласования |
| `GET/POST /api/tasks`, `PATCH /api/tasks/:id`, `POST /api/tasks/:id/escalate` | Задачи (MVP2) |
| `GET /api/diagnostics`, `GET /api/usage`, `GET /api/advisor` | Диагностика, использование продукта, ИИ-консультант |

**Бизнес-правила**, реализованные на сервере (`prototype/backend/rules.js`), а не в интерфейсе — соответствуют `requirements/02-system/business-rules-and-formulas.md` и `requirements/06-system-scenarios/system-scenarios.md`:

- классификация KPI по норме (`higher-better`, зеленый/желтый/красный по отношению факт/норматив);
- классификация магазина-аутсайдера (технический/бизнес-фактор/утилизация) на основе настраиваемых нормативов, а не жестко заданных меток;
- определение доступности кассы с учетом офлайн-режима: «Нет связи» не считается недоступностью, если касса подтверждена как функционирующая (`offline_but_available`);
- маршрут эскалации задачи РД → ОД;
- наследование региональных нормативов от сетевых с согласованием при занижении.

## Источник данных и примечания по безопасности

Все данные (`prototype/backend/seed.js`) — синтетические, сгенерированные по описанию из `requirements/`, аналогично `visual-prototype/data.js` (не выгрузка из реальной аналитики, не персональные данные). Секретов, реальных клиентских данных или продакшн-доступов в прототипе нет. Внешние интеграции (Kafka/ClickHouse/Superset/Set Centrum/ЦСЛ) не подключены — не требуются для проверки описанных сценариев на уровне «работает end-to-end на своей БД».

## Отклонения от визуального прототипа

1. **Классификация аутсайдера магазина №276 изменилась.** В `visual-prototype/data.js` магазин №276 был помечен меткой «Утилизация» (захардкожено). В прототипе классификация вычисляется реальным правилом (`classifyOutlier`), которое проверяет условия по порядку: доступность → доля SCO → утilизация. Поскольку у магазина №276 доля SCO (27%) ниже норматива (30%), он классифицируется как «Бизнес-фактор» раньше, чем доходит до проверки утилизации. Это не ошибка, а следствие того, что реальная бизнес-логика теперь действительно применяется, а не берется из статичной демо-метки — но интерфейс в этом конкретном случае показывает другую причину, чем в визуальном прототипе.
2. **Демо-переключатель состояний экрана переосмыслен.** В визуальном прототипе он подменял весь рендер целиком. В прототипе по умолчанию выполняется реальный запрос к API («авто»); принудительный выбор состояния (loading/empty/serverError) — по-прежнему доступен для демонстрации, но теперь явно обозначен как «(демо)», чтобы не путать с фактическим ответом сервера.
3. **Заявки в ИТ и статистика использования продукта не имеют интерфейса управления** сверх создания/просмотра — соответствует объему визуального прототипа, изменений нет.

Структура экранов, навигация, роли и визуальный язык (CSS/шрифты/палитра, скопированы без изменений из `visual-prototype/styles.css` и `i18n.js`) полностью соответствуют утвержденному визуальному прототипу.

## Упрощения и известные ограничения (нельзя переносить в production)

- **`node:sqlite`** — экспериментальный встроенный API Node.js (доступен с 22.5), выбран специально ради нулевых внешних зависимостей и мгновенного запуска. Для production нужна согласованная СУБД продукта (см. риски резидентности/масштаба в `requirements/03-architecture/technical-constraints.md`), а не легковесная встроенная БД.
- **Ручной роутинг на `node:http`** без Express/фреймворка — читаемо и достаточно для объема прототипа (14 маршрутов), но не рассчитан на рост API, отсутствуют мидлвары (CORS, rate-limiting, логирование запросов).
- **Агрегаты вместо сырых событий.** Доступность/доля SCO/утилизация хранятся как готовые числа на магазин, а не вычисляются из потока событий телеметрии (Kafka/ClickHouse/POSDWH) — реальный пайплайн агрегации телеметрии вне периметра прототипа и не может быть в нем воспроизведен без реального кассового оборудования.
- **Технические причины простоя не разбиты по магазину/кассе** — общий сетевой агрегат, как и в визуальном прототипе.
- **Аутентификации нет** — переключатель ролей демонстрационный (как и подтверждено Product Manager для этапа визуального прототипа), не для production.
- **Локализация** покрывает тот же представительный набор ключей, что и визуальный прототип — не исчерпывающий перевод всех строк.
- **Нет HTTPS/TLS**, инфраструктурных мер безопасности — не требуется для локальной демонстрации прототипа.

## Вопросы для проверки

1. Достаточно ли реализованных бизнес-правил (классификация KPI/аутсайдеров, доступность при офлайне, эскалация, наследование нормативов) для демонстрации клиенту, или нужна более полная модель (например, реальный расчет утилизации из сырых событий смены)?
2. Устраивает ли обнаруженное расхождение по магазину №276 (см. «Отклонения») — является ли это поводом скорректировать демо-данные, или, наоборот, ценной демонстрацией того, что реальные правила работают не так, как статичный мокап?
3. Нужен ли прототипу примитивный механизм аутентификации (хотя бы разделение по паролю на роль) для более реалистичной демонстрации, или текущий переключатель ролей достаточен для целей показа клиенту?
4. Подтверждается ли, что node:sqlite и ручной HTTP-роутинг — приемлемый технологический выбор именно для прототипа (не для финальной архитектуры), учитывая явное требование этапа не использовать эту архитектуру как финальную?
