## Анализ UI-кита

Локальный UI-кит (пакет компонентов или исходники) в рабочей директории не обнаружен — поиск по репозиторию (`package.json`, папки `ui-kit`/`design-system`/`components`) результатов не дал. В `requirements/04-quality/quality-requirements.md` есть только текстовое упоминание черновой дизайн-системы «Set · Эффективность» (типографика, палитра, отступы) как иллюстративного референса, явно не подключенного к процессу разработки. Компонентный маппинг в `02-screen.model.json` выполнен через типовые паттерны интерфейса («KPI-карточка», «таблица с фильтрами» и т.д.), а не через реальные компоненты — это остается открытым до появления исходников UI-кита в репозитории (не блокирует текущий этап).

## Возможности переиспользования компонентов

- **KPI-карточка с цветовой индикацией** — SCR-01, SCR-04, SCR-05, SCR-06, SCR-07, SCR-08.
- **Таблица с фильтрами/сортировкой и drill-down** — SCR-02, SCR-04/06/07 (таблицы «TOP аутсайдеров»), SCR-06 (технические причины), SCR-11, SCR-12.
- **Столбчатая диаграмма с линией норматива/тренда** — SCR-04, SCR-05, SCR-06, SCR-07.
- **Карточка задачи** — SCR-03 (список задач по магазину, MVP2) и SCR-09 (канбан-доска, MVP2).
- **Панель фильтров (период/магазин/касса/тип)** — повторяется на большинстве экранов, кандидат на единый переиспользуемый компонент.
- **RoleToggle (переключатель ролей)** — новый общий компонент для навигационной оболочки (см. ниже), используется во всех экранах, где отображение зависит от роли.
- SCR-04–SCR-07 — один и тот же «шаблон дашборда функционального блока» (KPI + диаграмма + таблица аутсайдеров), стоит спроектировать как один компонуемый шаблон.

## Недостающие компоненты

- **Канбан-доска с 3 колонками и карточкой задачи** (SCR-09, MVP2) — специфичный компонент, в стандартных UI-китах часто отсутствует.
- **Чат-панель для диалога с ИИ-консультантом** (SCR-13) — нестандартный компонент; теперь требуется для визуального прототипа (не только гипотетически).
- **Диаграмма утилизации с наложением двух рядов** (SCR-07) — нестандартная визуализация.
- **Компонент согласования нормативов** (SCR-08: запрос РД → подтверждение ОД) — комбинация формы и workflow-статуса.
- **Индикатор статуса кассы** (12 состояний) — нужен отдельный компонент-словарь статусов для SCR-03, SCR-06, SCR-11.
- **RoleToggle** — переключатель роли для демо-режима визуального прототипа (см. решение ниже) — нестандартный компонент, специфичный для мультиролевых demo-приложений.

## Навигационные проблемы — решено Product Manager (2026-07-21)

- **Навигационная оболочка.** Постоянная боковая навигация с прямым доступом к SCR-01, SCR-04, SCR-05, SCR-06, SCR-07 **и** drill-down из «Дашборда сети» (SCR-01) / «Карточки магазина» (SCR-03) — оба пути существуют одновременно. Зафиксировано в `02-screen.model.json` как `navigationShell`.
- **Переключение роли.** Для визуального прототипа — мгновенное переключение между тремя ролями (ОД/РД/ДМ) без реальной аутентификации (демо-режим, компонент `RoleToggle`). В production — один логин соответствует одной роли, определяется автоматически при входе. Зафиксировано как `roleSwitcher`.
- **Маршрут эскалации задачи (SCR-09, MVP2).** Подтверждено: эскалация идет по цепочке РД → ОД (если РД тоже не отреагировал). Зафиксировано в `requirements/07-scenarios/business-scenarios.md` и в обеих моделях.
- **SCR-06 → SCR-10.** Экраны объединены: детальный отчет о технических причинах недоступности теперь часть SCR-06, общая для всех ролей (включая технические службы), а не отдельный ограниченный экран. SCR-10 удален из моделей как самостоятельный экран.

## UX-риски

- **Один и тот же экран (SCR-04–SCR-07) отображается с разным объемом данных в зависимости от роли** (ОД — вся сеть, РД — регион, ДМ — свой магазин). Интерфейс должен явно сигнализировать пользователю, на каком уровне агрегации он находится — не решено, перенесено на этап визуального прототипа.
- **Разнонаправленная цветовая индикация между блоками.** Для «Производительности» рост отклонения — плохо (красный), для «Доступности» рост показателя — хорошо (зеленый). Компонент KPI-карточки должен быть параметризован по направлению шкалы — не решено, перенесено на этап визуального прототипа.
- **Локализация (RU/EN через таблицу ключей)** — сквозное требование ко всем экранам; компоненты должны с самого начала использовать ключи, а не захардкоженный текст.
- **SCR-09 и SCR-13 — не MVP1.** При переходе к визуальному прототипу нужно явно маркировать эти экраны, чтобы их не спутали с экранами, готовыми к разработке в текущем релизе (SCR-09 — подтвержденный MVP2, SCR-13 — включен только в демонстрационный прототип, без подтвержденного релиза).

- ~~Служба поддержки имеет «полный доступ» без уточнения, включает ли он коммерческие данные~~ — **решено**: включает коммерческие метрики (выручка, доля SCO), в отличие от «технических служб».

### Дополнительные исправления бизнес-правил (Product Manager, 2026-07-21)

- **Офлайн-режим касс.** SCR-06 (Дашборд доступности касс) и словарь состояний (`entities-and-data-dictionary.md`) уточнены: временная потеря связи с сервером сама по себе не делает кассу недоступной, если она продолжает функционировать и накапливает данные локально для последующей передачи без потерь.
- **Исправлена формула доступности SCO** в `requirements/02-system/business-rules-and-formulas.md` (была внутренняя нестыковка источников Confluence) — не затрагивает структуру SCR-06, только корректность данных.
- **SCR-08 переименован и расширен**: «Настройка нормативов и порогов», теперь включает также пороги утилизации POS/SCO (ранее фигурировали как фиксированные значения в бизнес-правилах). Экран явно выведен из состава `navigationShell` — это отдельное приложение настроек, а не часть основной навигации аналитического продукта.
- **Формализована сущность «Задача»** отдельным требованием `requirements/02-system/task-management.md` — SCR-03 и SCR-09 теперь опираются на явно описанную функциональность, а не только на сценарий и упоминание в концепции ИИ-консультанта.
- **Роли в сценарии «Оптимизация нагрузки и ресурсов» уточнены** (ОД vs РД) — не влияет на модель экранов напрямую (роли в `02-screen.model.json` уже были заданы явно через ID), но убирает несогласованность с исходным текстовым сценарием.

## Не блокирующие вопросы (перенесены из `ai-artifacts/needs-input.md`, не блокируют эту модель)

- Точные идентификаторы полей/событий в системе Set (влияет на `dataRequirements`, не на структуру экранов).
- Полнота перечня технических причин недоступности (страница Confluence вне дерева требований) — может повлиять на состав объединенного технического блока в SCR-06.
- Статус и приоритет ИИ-консультанта в общей продуктовой дорожной карте (MVP1/MVP2/отдельный этап) — включение демо-версии в визуальный прототип не отвечает на этот вопрос.
- Расшифровка «ЦСЛ», протокол интеграции, аутентификация/retry-политики — не отображаются на экранах, влияют только на бэкенд-интеграции.
- Два технических риска (дублирование чеков при смене master-кассы; точный подход к логированию платформы) — архитектурные, не экранные.
