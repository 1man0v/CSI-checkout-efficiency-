# Технические ограничения

Источник: Confluence 6318325801, 6323437618.

## Обязательный технологический стек

Функциональность должна использовать единый стек отчетности Set:

- Kafka — транспорт событий телеметрии;
- POSDWH / DWH — хранение и агрегация данных;
- ClickHouse — аналитическое хранилище агрегатов, к которому обращаются аналитические модули;
- Apache Superset — построение отчетов;
- Set Centrum — встраивание дашбордов (конечная точка визуализации для пользователей).

Это ограничение зафиксировано явно в исходном документе как обязательное («Система должна строиться на едином аналитическом стеке»), а не как предложение архитектора.

## Хранение и агрегация данных

- Хранение сырых событий (телеметрия с касс).
- Хранение агрегатов (почасовых и суточных).
- Отправка агрегированных данных в ЦСЛ: почасовые агрегаты и суточные агрегаты.
- Расчет медиан и p90/p95 по ключевым метрикам.
- Суточные агрегаты идентифицируются по: Set ID, номер магазина, номер кассы, тип кассы (POS/SCO/TOUCH/HYBRID) — см. `requirements/02-system/entities-and-data-dictionary.md`.

## Сбор телеметрии на кассах

- Heartbeat с периодичностью 1 минута о состоянии кассы (доступна/недоступна) — обязательная частота опроса, зафиксирована явно.
- Часть данных уже собирается на уровне касс под управлением ПО Set (POS/Touch/SCO/Hybrid); часть данных потребуется добавить (см. NEEDS_INPUT в `requirements/02-system/entities-and-data-dictionary.md` по конкретным идентификаторам полей).
- Требуется хранение данных на кассах в offline режиме (см. также `requirements/04-quality/quality-requirements.md`).

**Работа в офлайн-режиме и синхронизация (подтверждено Product Manager, 2026-07-21).** При потере связи с центральным сервером касса продолжает работать локально и должна:

- накапливать (буферизовать) все относящиеся к телеметрии события локально на кассе на весь период отсутствия связи (события чека, состояния кассы, heartbeat);
- при восстановлении связи передать накопленные данные в систему **без потери и без искажения объема и целостности данных** — то есть гарантированная, а не best-effort доставка буфера (детальный протокол передачи/подтверждения доставки — предмет технического проектирования, не бизнес-требования).

Это напрямую влияет на бизнес-логику доступности кассы: сам факт офлайн-режима не считается недоступностью — см. `requirements/06-system-scenarios/system-scenarios.md` и `requirements/02-system/user-roles-and-functional-blocks.md` (Функциональный блок 3).

## Инфраструктурные ограничения

- Система предполагает хранение и обработку большого объема данных от POS/SCO в режиме, близком к реальному времени — это создает нагрузку на инфраструктуру, отмеченную как риск проекта.
- Внедрение требует доработок по отправке телеметрии на кассах, настройки POSDWH, настройки ClickHouse, интеграции Superset и настройки дашбордов — отмечено как риск «сложность внедрения».

## Настраиваемые параметры — отдельное приложение (подтверждено Product Manager, 2026-07-21)

Все настраиваемые пороговые значения (нормативы p95/median по производительности и доступности, пороги утилизации POS/SCO и т.п.) должны быть вынесены в **отдельное приложение настроек**, а не быть зашиты в логику аналитических дашбордов и не быть частью основной навигационной оболочки продукта. Затрагивает архитектуру поставки (отдельная точка входа/модуль, встраиваемый в Set Centrum отдельно от аналитических отчетов) — см. `ai-artifacts/02-screen.model.json` (SCR-08).

## Модель развертывания (подтверждено Product Manager, 2026-07-20)

Развертывание — on-premise у торговой сети, с доступом для сотрудников СЭТ (вендора/поставщика решения) для эксплуатации и поддержки. Модель «облако Set» и «гибрид» не выбраны.

## Версии компонентов стека и резидентность данных (подтверждено Product Manager, 2026-07-20)

- Версии компонентов стека (Kafka/ClickHouse/Superset и др.) отдельно не фиксируются — они выпускаются релизами вместе с Set Retail, так как на кассах могут появляться новые метрики, а серверы и шины данных могут обновляться в рамках релизного цикла Set Retail.
- Резидентность данных: данные физически остаются в контуре сети (on-premise, см. выше).
- Доступ сотрудников СЭТ к инфраструктуре — через VPN с аудитом сессий.
