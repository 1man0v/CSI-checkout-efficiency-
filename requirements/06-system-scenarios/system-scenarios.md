# Системные и операционные сценарии

Источник: Confluence 6318325801, 6323437618, 6381666307.

## Мониторинг доступности кассы через heartbeat

Каждая касса (POS/Touch/SCO/Hybrid) отправляет heartbeat с периодичностью 1 минута, сигнализирующий о состоянии «доступна» / «недоступна». Отсутствие heartbeat в ожидаемый интервал само по себе означает офлайн-режим (потерю связи с центральным сервером), а не автоматически «недоступность» кассы — см. уточнение ниже (подтверждено Product Manager, 2026-07-21).

Касса считается доступной для покупателя, когда одновременно выполняются все условия:

- касса в режиме ожидания покупателя или идет продажа;
- открыта смена;
- нет блокировки кассы консультантом;
- нет ошибки ККТ, ошибки ответа банка, ошибки отсутствия бумаги;
- весы в нуле, нет ошибки весов;
- нет окна с ошибкой, требующей действий покупателя/консультанта;
- нет открытого чека без активности при выключенной автоаннуляции.

**Работа в офлайн-режиме (подтверждено Product Manager, 2026-07-21).** КСО или POS могут временно терять связь с центральным сервером, продолжая работать локально. В такой реализации касса, работающая в офлайн-режиме, **считается доступной**, если остальные условия из списка выше выполняются. Для этого касса должна:

1. накапливать метрики (события чека, состояния, heartbeat) локально, пока нет связи;
2. при восстановлении связи передать накопленные данные в систему целиком, без потери и без искажения объема данных (см. `requirements/03-architecture/technical-constraints.md`).

Реальный статус кассы за период отсутствия связи (доступна / недоступна по иной причине — нет бумаги, ошибка банка и т.д.) определяется постфактум по данным, накопленным на кассе, а не приравнивается автоматически к «недоступности» из-за самого факта отсутствия связи. «Длительность нахождения оффлайн» (отсутствие heartbeat) продолжает фиксироваться отдельно в суточных агрегатах как техническая метрика связи — см. `requirements/02-system/entities-and-data-dictionary.md` — но не смешивается с бизнес-метрикой доступности кассы для покупателя.

Полный перечень фиксируемых состояний кассы — см. раздел «Состояния SCO» в `requirements/02-system/entities-and-data-dictionary.md`.

## Реакция на аппаратные ошибки (сценарий анализа, а не автоматизации)

Документы описывают этот сценарий как аналитический (для последующего расследования директором/региональным директором), а не как автоматическую реакцию системы:

1. Касса переходит в состояние ошибки (нет бумаги / ошибка банка / ошибка весов / ошибка сканера / ошибка принтера / нет связи).
2. Событие и длительность нахождения в состоянии фиксируются в агрегатах.
3. На дашборде «Причины недоступности» состояние подсвечивается как аномалия, если длительность простоя превышает медиану по сети.
4. Ответственная роль (ДМ/РД) получает рекомендацию (например, «заявка в ИТ-отдел/банк-эквайер» для ошибки банка, «работа с дисциплиной персонала» для блокировки сотрудником).

Автоматических действий системы (перезапуск кассы, автоматическое уведомление ИТ и т.п.) исходные документы не описывают.

## Ввод магазина/кассы в эксплуатацию и возврат из ремонта (подтверждено Product Manager, 2026-07-20)

В аналитическом модуле нет отдельного ручного шага «регистрации» нового магазина или кассы. Появление и выбытие объектов определяется автоматически по данным, поступающим из Set Retail:

- новый магазин или касса появляются в отчетности автоматически, как только от них начинает поступать телеметрия (см. heartbeat, `requirements/03-architecture/technical-constraints.md`);
- при недоступности кассы (в текущем или в прошлом периоде) касса **не должна пропадать из отчетности** — она остается видимой и помечается как недоступная/оффлайн (см. состояния кассы в `requirements/02-system/entities-and-data-dictionary.md`);
- возврат кассы из ремонта или из оффлайна не требует отдельного сценария «ввода в эксплуатацию» — система должна просто зафиксировать возобновление heartbeat и снова отражать кассу как доступную.

## Синхронизация и кластеризация касс — рабочее допущение (подтверждено Product Manager, 2026-07-20)

Рабочее допущение, подтвержденное Product Manager: аналитический модуль не реализует собственную бизнес-логику для сценариев «master-касса в магазине» и «разделение касс по кластерам» — это зона ответственности кассового ПО Set Retail, а не аналитического модуля. Аналитика опирается на то, что `Set ID`/номер кассы остаются стабильными и уникальными независимо от того, как кассы синхронизируются между собой. Это подтвержденное решение о выведении сценария за пределы объема продукта (out of scope), а не отложенное решение.

## NEEDS_INPUT: Технический риск — дублирование/потеря чеков при смене master-кассы

Статус: NEEDS_INPUT (не блокирует модель продукта — требует технической проверки)

Вопрос: Может ли смена master-кассы или переключение между вариантами синхронизации приводить к дублированию или потере чеков в данных, которые получает аналитический модуль?

Контекст: Product Manager подтвердил, что этот вопрос нужно уточнить у архитекторов Set Retail, а не решать на уровне продуктовых требований аналитического модуля. До получения ответа действует рабочее допущение выше.

Почему это важно: Если смена master может приводить к дублированию/потере чеков, аналитическому модулю потребуется отдельная логика дедупликации — технический риск для последующих этапов, но не блокер для готовности модели продукта (сценарий синхронизации/кластеризации явно исключен из зоны ответственности продукта).

## Поставка, установка, обновление, логирование и мониторинг платформы (подтверждено Product Manager, 2026-07-20)

- **Поставка, установка, обновление:** тем же релизным механизмом, что и весь Set Retail. Версионность и релизы аналитической платформы идут вместе с релизной сеткой Set Retail 10 — отдельного процесса поставки/установки для этого модуля не существует.
- **Логирование и мониторинг:** используется единый лог-агрегатор, аналогичный применяемому в продуктах Set Retail (единый подход для всей экосистемы, а не отдельное решение для этого модуля).
- **Сбор метрик платформы:** отдельно не задан — исходя из подтвержденного подхода, ожидается использование того же механизма, что и для логирования/мониторинга (единый лог-агрегатор Set Retail).

## NEEDS_INPUT: Точный подход к логированию платформы

Статус: NEEDS_INPUT (не блокирует модель продукта — требует технической проверки)

Вопрос: Какой конкретно единый лог-агрегатор используется в продуктах Set Retail, и как аналитическая платформа (Kafka/DWH/ClickHouse/Superset) должна к нему подключаться?

Контекст: Product Manager подтвердил направление (логирование через существующий единый лог-агрегатор Set Retail), но явно указал, что точный подход требует уточнения у архитектора.

Почему это важно: Технический риск для этапов проектирования архитектуры и эксплуатации, но не блокер для готовности модели продукта — направление и владелец решения (архитектор) уже определены Product Manager.
