# Нефункциональные требования

Источник: Confluence 6318325801, 6323437618.

## Производительность и актуальность данных

- Работа с большими объемами данных.
- Требование «обновление данных, близкое к реальному времени» из исходного документа Confluence уточнено Product Manager для MVP1 — см. «Целевые показатели NFR» ниже: для MVP1 самого по себе near-realtime не требуется.

## Масштабируемость и надежность

- Поддержка крупных торговых сетей.
- Горизонтальное масштабирование.
- Масштабируемость на крупные торговые сети (дублируется в обоих исходных документах — единое требование).
- Возможность работы в высокодоступной схеме (отказоустойчивость).
- Хранение данных на кассах в offline режиме (устойчивость к потере связи).

## Визуализация и удобство использования

- Простая и эффективная визуализация.
- Аналитика от всей сети с погружением до уровня отдельных касс (drill-down).
- Возможность встраивания дашбордов в Set Centrum.
- Поддержка кастомных дашбордов в будущем.

## Хранение данных

- Поддержка длительного хранения телеметрии.

## Безопасность и разграничение доступа

- Поддержка разграничения доступа у ролей пользователей (соответствует ролям ОД/РД/ДМ и, вероятно, дополнительным ролям — см. NEEDS_INPUT в `requirements/02-system/user-roles-and-functional-blocks.md`).

## Дизайн-система (иллюстративный референс, статус «Черновик»)

Существует предложенная дизайн-система «Set · Эффективность» (Confluence 6487081052): две гарнитуры (IBM Plex Sans для интерфейса, IBM Plex Mono для чисел/KPI), плоские карточки без теней, шкала отступов на основе 4px, статус передается цветом (не иконками). Явно зафиксировано, что это **не** наследование существующего бренда Set/Crystals, а отдельное предложение, не подключенное к процессу разработки и требующее ревью перед продакшн-использованием — то есть не является утвержденным нефункциональным требованием к UI, а лишь референсом.

## Целевые показатели NFR (подтверждено Product Manager, 2026-07-20; уточнено 2026-07-20)

- **Задержка обновления данных для MVP1:** near-realtime **не требуется**. Product Manager подтвердил, что близкая к реальному времени задержка нужна только для проактивного сценария ИИ-агента (автопостановка задачи по LFL-прогнозу, см. `requirements/02-system/ai-advisor-concept.md`), а этот сценарий явно вне MVP1/MVP2. Для дашбордов и отчетов MVP1 достаточно периодической агрегации данных — почасовых и суточных агрегатов, уже описанных в `requirements/03-architecture/technical-constraints.md`. Это уточняет (сужает) исходное требование Confluence «обновление данных близкое к реальному времени», которое было сформулировано без привязки к конкретному релизу.
- **Отказоустойчивость (SLA):** стандартный уровень для решений такого класса — 99%.
- **Срок хранения телеметрии:** бессрочный. Автоматическая обрезка/TTL не предусмотрены; обрезка данных выполняется вручную силами инженера сервиса при необходимости. Это принципиальное требование: ИИ-агент должен иметь возможность анализировать LFL на длительных периодах, что требует полной истории телеметрии, а не только недавнего окна данных (актуально независимо от статуса ИИ-агента в дорожной карте — хранение нужно начинать с MVP1, чтобы история была доступна к моменту реализации).

## Ожидаемый масштаб / сайзинг (подтверждено Product Manager, 2026-07-20; единицы измерения согласованы 2026-07-20)

Референсные профили торговой сети, под которые рассчитывается инфраструктура. По уточнению Product Manager все профили заданы в единых единицах — количество касс суммарно по сети (а не на магазин), чтобы профили были сопоставимы между собой:

| Профиль сети | Магазинов | Касс (суммарно по сети) |
| --- | --- | --- |
| Малая сеть | до 100 | до 300 |
| Средняя сеть | до 500 | до 1000 |
| Крупная сеть | от 500 | свыше 1000 |

Точное количество событий телеметрии в секунду отдельным бизнес-требованием не задается — рассчитывается инженерно из подтвержденной частоты heartbeat (1 раз в минуту на кассу, см. `requirements/03-architecture/technical-constraints.md`) и объема чековых событий (`requirements/02-system/entities-and-data-dictionary.md`) применительно к каждому профилю сети.

## Локализация (подтверждено Product Manager, 2026-07-20)

- Поддерживаемые языки: русский и английский по умолчанию; другие языки — по запросу.
- Требуется таблица локализации с ключами в продукте: контент ведется через ключи, эталонный язык для переводчиков — английский; перевод на любой другой язык выполняется только на основе таблиц локализации (без хардкода текста в коде/дашбордах).
