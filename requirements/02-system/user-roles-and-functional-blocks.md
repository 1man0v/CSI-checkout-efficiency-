# Роли пользователей и функциональные блоки

Источник: Confluence 6318325801, 6133710853, 6323437618.

## Роли и их фокус

### Операционный директор (ОД)

Смотрит на «здоровье» всей сети.

- Выполнение годового KPI по доле чеков КСО (рост с 20% до 28%).
- Минимизация упущенного оборота из-за недоступных касс.
- Выявление неэффективных магазинов.
- Оптимизация затрат на персонал.

### Региональный директор (РД)

- KPI конкретного «куста» (региона).
- Выравнивание магазинов-аутсайдеров под общий норматив.
- Оптимизация штатного расписания.
- Выявление недонагруженных КСО.
- Оптимизация персонала и расписания на избыточно открытых POS для снижения затрат.

### Директор магазина (ДМ)

- Оперативное управление зоной расчета.
- Контроль доступности касс.
- Управление очередями.

Пошаговый сценарий работы ДМ в системе — см. `requirements/07-scenarios/business-scenarios.md` («Сценарий: Директор магазина — получение и выполнение задачи»).

### Технические службы, служба поддержки, продуктовые команды (роли и функции подтверждены Product Manager, 2026-07-20)

Это отдельные пользовательские роли системы, а не только адресаты аналитики.

- **Технические службы** — доступ к отчету «Причины недоступности» и техническим метрикам оборудования (ошибки ККТ/банка/сканера/весов), без коммерческих KPI (доля SCO, выручка); интеграция с системой заявок в ИТ (тикеты).
- **Служба поддержки** (поддержка CSI / ИТ-служба клиента) — полный доступ для поиска проблем, ошибок, выявления причин поломок, **включая коммерческие метрики (выручка, доля SCO)** (подтверждено Product Manager, 2026-07-21). Доступ шире, чем у технических служб — не ограничен только техническими причинами и не исключает коммерческие показатели.
- **Продуктовые команды** — двойной доступ: (1) бизнес-аналитика по торговой сети — эффективность работы КСО и проблем, как у ОД/РД; (2) аналитика использования самого продукта (какие отчеты открывают чаще, где чаще всплывают аномалии) для приоритизации доработок продукта.

### Резюме ценности для роли («Что я получу из этого инструмента?»)

1. Понимание реальной причины очередей: сломалась техника или не хватает кассиров/КСО.
2. Обоснование для сокращения/увеличения штата: данные по «чекам, доступным для КСО» показывают, сколько кассиров выполняют работу, которую могла бы сделать машина.
3. Контроль дисциплины: выявление касс, которые формально включены, но не приносят выручку (низкое среднее время в режиме продажи).
4. Технический контроль: выявление топ причин простоев по аппаратной части для передачи заявок в ИТ.

## Используемые отчеты (для ОД/РД)

1. Главный дашборд состояния сети/сегмента — доступность КСО, доля чеков на КСО.
2. Анализ эффективности сегментов — топ аутсайдеров в табличном виде с параметрами.
3. Причины недоступности SCO — технический фактор, бизнес-фактор.
4. Упущенная эффективность — потоки покупателей, утилизация ресурсов касс.

## Функциональный блок 1: Производительность касс (POS vs SCO)

**Назначение:** анализ скорости обслуживания покупателей на POS и SCO и выявление технических/операционных проблем, влияющих на пропускную способность магазина.

**Собираемые показатели:** время добавления товара; время добавления маркированного товара; количество товаров в чеке; количество маркированных товаров в чеке; время расчета скидок в чеке; время расчета скидок при переходе к оплате; время оплаты; тип оплаты; время печати чека; продолжительность аннулированного чека; общее время покупки; количество чеков; тип кассы (POS/Touch/SCO/Hybrid); идентификатор магазина; идентификатор кассы.

**Формула:** производительность = (время на товар × количество товаров) + (время на маркированный товар × количество маркированных товаров) + время расчета скидок + время оплаты + время печати — с привязкой к конкретному времени чека и кассе в магазине.

**Визуализация:**
- KPI-плашки: текущее p95 (сек) за период для каждого типа касс POS/TOUCH/SCO/Hybrid; отклонение в секундах и в процентах за весь диапазон данных для каждого типа. Цветовая индикация: до 15% — зеленый, 16–70% — желтый, ≥70% — красный.
- Почасовые графики: POS — столбчатая диаграмма; SCO — столбчатая диаграмма; линия норматива p95.
- Детализация причин снижения: медленное сканирование, проблемы с маркировкой, долгие оплаты, медленная печать, ошибки ККТ, медленные кассиры, ошибки весов/сканеров. Проблемные магазины — в табличном виде внизу отчета.

## Функциональный блок 2: Соотношение покупок и потенциал SCO

**Назначение:** анализ распределения потока покупателей между POS и SCO, оценка упущенного потенциала самообслуживания.

**Собираемые показатели:** количество чеков, зарегистрированных на POS/SCO; способ оплаты (наличные/безналичные); количество товаров в чеке; время покупки; номер магазина; номер кассы.

**Формула потенциального SCO-чека:** количество товаров в чеке ≤ 10 и тип оплаты — безналичный.

**Визуализация:**
- KPI-плашки: фактическая доля SCO, фактическая доля POS.
- Pie chart: фактическое соотношение POS/SCO; потенциал SCO (доля чеков POS > 10 товаров + наличная оплата / доля чеков SCO / доля чеков POS ≤ 10 товаров с безналичной оплатой).
- Столбчатая сложенная диаграмма: почасовое распределение потоков POS/SCO; линия тренда для POS = p95 количества чеков POS >10 товаров + наличная оплата, установленная на среднем значении за весь период.

## Функциональный блок 3: Доступность касс (Uptime)

**Назначение:** контроль фактической доступности касс для покупателей, выявление причин простоев.

**Условия, когда SCO считается доступной для покупателя:** касса в режиме ожидания покупателя или идет продажа; открыта смена; нет блокировки кассы консультантом; нет ошибки ККТ; нет ошибки ответа банка; нет ошибки отсутствия бумаги; весы в нуле, нет ошибки весов; нет окна с ошибкой, требующей действий покупателя/консультанта (возраст, марка и т.п.); нет открытого чека без активности при выключенной автоаннуляции.

**Уточнение по офлайн-режиму (подтверждено Product Manager, 2026-07-21):** отсутствие связи с центральным сервером (офлайн-режим) само по себе **не** делает кассу недоступной. Касса, работающая в офлайн-режиме, но фактически способная обслуживать покупателя (нет прочих ошибок из списка выше), считается доступной. Для этого касса должна накапливать метрики локально во время отсутствия связи и передавать их в систему при восстановлении соединения без потери качества и целостности объема данных — см. требование в `requirements/03-architecture/technical-constraints.md`. Реальный статус кассы за офлайн-период (доступна или недоступна по иной причине) определяется по данным, накопленным на кассе, а не по факту отсутствия связи.

**Собираемые данные:** номер магазина; номер кассы; heartbeat с периодичностью 1 минута о состоянии кассы (доступна/недоступна).

**Формула:** доступность = (время доступности кассы для покупки / время работы магазина) × 100%.

**Визуализация:**
- KPI-плашки: фактическая доступность SCO (%); отклонение (%) за весь диапазон данных. Цветовая индикация: до 15% — красный, 16–70% — желтый, ≥70% — зеленый.
- Столбчатая сложенная диаграмма доступности по дням (часы доступности снизу + часы недоступности сверху) с линией тренда.
- Столбчатая сложенная диаграмма доступности по часам суток, аналогично.
- Таблица «TOP аутсайдеров»: магазин, касса, часы доступности, часы недоступности.

## Функциональный блок 4: Утилизация ресурсов (и прогноз нагрузки — MVP2)

**Назначение:** анализ фактической загрузки POS/SCO, прогнозирование риска очередей (прогноз — MVP2).

**Собираемые данные:** общее время чека (POS/SCO) с привязкой ко времени окончания чека; время сессии кассира (смена открыта, вход под своей ролью, касса разблокирована); uptime SCO; номер кассы; номер магазина.

**Формулы утилизации:**
- POS: время в чеке / время сессии кассира × 100%.
- SCO: время в чеке / uptime кассы × 100%.

Время работы магазина желательно задавать вручную либо использовать фактические данные (время открытия первой смены/первого логина и время закрытия последней смены/последнего логина в сутках).

**Визуализация:**
- KPI-плашки: % утилизации POS, % утилизации SCO.
- Столбчатая диаграмма утилизации SCO с наложением: часы SCO в чеке поверх часов доступности SCO по оси Y, часы суток по оси X, линия тренда.
- Аналогичная диаграмма утилизации POS: часы нахождения в чеке поверх часов присутствия кассира.
- Таблица «TOP аутсайдеров»: магазин, касса, часы утилизации, часы доступности.

## Права доступа по ролям (подтверждено Product Manager, 2026-07-20)

| Роль | Область данных (data scope) | Права/действия |
| --- | --- | --- |
| Операционный директор (ОД) | Вся сеть | Просмотр всех отчетов; ручная простановка нормативов на уровне сети; экспорт; постановка задач РД и ДМ. |
| Региональный директор (РД) | Свой кластер/регион | Просмотр отчетов региона; постановка и делегирование задач ДМ; работа с задачами, поставленными ОД; **может** менять нормативы для своего региона, но **не может** менять регион или нормативы сети целиком; снижение норматива региона ниже сетевого норматива ОД — только через согласование с ОД. |
| Директор магазина (ДМ) | Свой магазин | Просмотр отчетов своего магазина; выполнение и закрытие задач; **не может** ставить нормативы. |

Функции, связанные с постановкой задач и контролем их выполнения, относятся к MVP1 (перенесено из MVP2 решением Product Manager 2026-07-22, см. `requirements/01-base/product-context.md`). Маршрут эскалации невыполненной задачи: РД → ОД (см. `requirements/07-scenarios/business-scenarios.md`).

Права доступа для ролей «технические службы», «служба поддержки», «продуктовые команды» описаны в разделе «Технические службы, служба поддержки, продуктовые команды» выше (объем доступа к данным определен через их функции; отдельная матрица «просмотр/редактирование» для них не формализована — эти роли по описанным функциям являются потребителями отчетов, без функций редактирования нормативов или управления задачами).
