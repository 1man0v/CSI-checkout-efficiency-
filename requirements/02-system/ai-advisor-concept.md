# Концепция операционного ИИ-консультанта Set Retail Pro

Источник: Confluence 6446514277. Статус в исходном документе: концептуальное предложение, не входит в MVP1/MVP2 основного продуктового решения (см. `requirements/01-base/product-context.md`).

## Цель

Интеллектуальный слой над аналитической платформой, позволяющий руководителю получать ответы на естественном языке (например, «Что сегодня мешает эффективности магазина?», «Почему выросли очереди?», «Почему доля КСО ниже ожидаемой?»). Цель — не генерация текста, а автоматическое расследование причин снижения эффективности на основе данных аналитической платформы, с ссылками на конкретные аналитические модули продукта.

## Проактивный сценарий: автоматическая постановка задач по прогнозу LFL (подтверждено Product Manager, 2026-07-20)

В дополнение к режиму «вопрос-ответ», описанному в исходном документе Confluence, Product Manager подтвердил проактивный режим работы: система должна уметь самостоятельно инициировать задачу, а не только отвечать на вопрос пользователя.

Пример: в магазине 3 КСО и 2 POS, но фактически работает только 1 POS. По модели LFL (like-for-like) на вечер ожидается поток покупателей, который эта конфигурация не обработает — возникает риск перегрузки и очередей. В этом случае система должна автоматически поставить задачу директору магазина, не дожидаясь его вопроса.

Это требование прямо связано с нефункциональным требованием «задержка обновления данных, близкая к реальному времени» (см. `requirements/04-quality/quality-requirements.md`) и с долгосрочным хранением телеметрии без TTL (необходимо для LFL-прогноза на длительных периодах).

Статус в дорожной карте (MVP1/MVP2/отдельный этап) не определен — см. `NEEDS_INPUT: Статус и приоритет ИИ-консультанта в дорожной карте` ниже; это уточнение не меняет открытый вопрос, а расширяет его контекст.

## Принцип: два независимых уровня

1. **Аналитическая платформа** — основной продукт (см. остальные файлы `requirements/02-system/`).
2. **Интеллектуальный консультант** — надстройка, описанная в этом файле.

Ключевой принцип: языковая модель **не анализирует сырые данные напрямую** и **не принимает аналитических решений** — только интерпретирует запрос пользователя и формулирует ответ. Логика находится в управляемых правилах, аналитических модулях, гипотезах и рекомендациях.

## Конвейер обработки запроса

```
Вопрос пользователя
→ Смысловой маршрутизатор
→ Выбор сценариев расследования
→ Запуск аналитических модулей
→ Получение фактов
→ Проверка гипотез
→ Формирование рекомендаций
→ Языковое оформление ответа
```

## Компоненты

- **Расследование** — заранее описанный сценарий проверки класса проблем: указывает, какие аналитические модули запустить и какие гипотезы проверить. Не содержит SQL и не считает показатели само.
- **Смысловой маршрутизатор** — сопоставляет вопрос пользователя с зарегистрированными расследованиями через эмбеддинги (сравнение эмбеддинга вопроса с эмбеддингами описаний расследований); может выбрать одно или несколько расследований.
- **Аналитический модуль** — расчетный блок продукта по предметной области (производительность магазина/POS/КСО, доступность КСО, простои, очереди, сравнение магазинов, потенциал КСО); обращается к ClickHouse и возвращает структурированные факты.
- **Гипотеза** — формализованная возможная причина проблемы, заранее описанная в реестре (не создается динамически из текста); имеет список нужных фактов и условия подтверждения.
- **Уверенность** — рассчитывается по правилам (базовое значение + надбавки за выполнение конкретных условий); при неполном подтверждении гипотеза может получить статус «частично подтверждена» или «требует проверки».
- **Рекомендация** — привязана к конкретной подтвержденной гипотезе (не генерируется языковой моделью произвольно), содержит текст, приоритет и ожидаемый эффект.

## Роль локальной языковой модели

Может: переформулировать ответ, задать уточняющий вопрос, сделать ответ понятнее, поддерживать диалог.

Не должна: писать произвольные запросы к данным, самостоятельно подтверждать гипотезы, придумывать рекомендации без связи с фактами, изменять бизнес-логику.

## Заявленные преимущества подхода

- Объяснимость — каждый вывод прослеживается: ответ → рекомендация → подтвержденная гипотеза → факты → аналитический модуль → данные.
- Управляемость — бизнес-логика не скрыта в языковой модели, а описана в расследованиях/гипотезах/рекомендациях.
- Масштабируемость — новые модули, расследования, гипотезы и рекомендации добавляются независимо.
- Работа внутри контура заказчика — решение не требует передачи данных во внешние сервисы.
- Независимость от конкретной модели — языковую модель можно заменить без изменения аналитического ядра.
