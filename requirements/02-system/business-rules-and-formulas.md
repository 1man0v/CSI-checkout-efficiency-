# Бизнес-правила и формулы расчета метрик

Источник: Confluence 6381666307, 6323437618, 6133710853.

## Бизнес KPI MVP

| KPI | Цель |
| --- | --- |
| Доля чеков SCO | Рост с 20% до 28% |
| Доступность SCO | > 90% |
| Утилизация SCO | Рост по сети |
| Количество магазинов-аутсайдеров | Снижение |
| Потенциальные чеки SCO | Снижение объема чеков на POS |

## Верхнеуровневые нормативы (главный дашборд)

- **Доступность КСО.** Норматив: > 90%. Расчет: (время, когда КСО были доступны для покупки / время работы магазина) × 100%. Авто-норматив (если не задан вручную): медиана по аналогичным форматам (или сети) магазинов за весь доступный период.
- **Доля чеков КСО.** Норматив: > 30%. Расчет: (количество чеков на SCO / количество чеков на POS) × 100%. Авто-норматив — аналогично медиане по формату/сети.

## Формулы бизнес-показателей для суточных агрегатов

### 1. Доступность SCO

**Исправлено Product Manager, 2026-07-21:** формула ниже ранее была ошибочно приведена как «длительность доступности / длительность в чеке × 100» (артефакт несогласованности исходных документов Confluence — на разных страницах встречались два разных варианта). Корректная формула — та же, что уже используется в «Верхнеуровневые нормативы» выше и в `requirements/02-system/user-roles-and-functional-blocks.md`:

```
доступность = время, когда касса была доступна для покупки / время работы магазина × 100
```

Норматив: > 90%. Учитывается уточнение по офлайн-режиму — см. `requirements/06-system-scenarios/system-scenarios.md`: сам факт отсутствия связи с сервером не считается недоступностью, если касса продолжает функционировать (данные накапливаются локально и передаются при восстановлении связи).

### 2. Утилизация SCO

```
утилизация SCO = длительность в продаже / длительность доступности × 100
```

### 3. Утилизация POS

```
утилизация POS = длительность в продаже / длительность смены × 100
```

### 4. Доля чеков SCO

```
доля SCO = чеки, зарегистрированные на SCO / все чеки магазина × 100
```

### 5. Потенциал SCO

Определение потенциального SCO-чека на POS: количество товаров в чеке ≤ 10 и тип оплаты ≠ наличные.

```
потенциальные SCO-чеки = количество чеков POS, удовлетворяющих условию выше
```

### 6. Упущенная эффективность

```
упущенная эффективность = потенциальные SCO-чеки − доля чеков SCO
```

### 7. Недоступность SCO

Определяется по идентификатору состояния SCO (см. «Состояния SCO» в `entities-and-data-dictionary.md`) и длительности нахождения в этом состоянии.

### 8. Доступность POS (добавлено в прототипе, требует подтверждения Product Manager)

При доработке прототипа (доработка блока POS: доступность, число чеков, технические сбои — без
операционных/кадровых причин) добавлена доступность POS как отдельная метрика, по той же формуле,
что и доступность SCO:

```
доступность POS = время, когда касса POS была доступна для обслуживания / время работы магазина × 100
```

**Норматив 95%, используемый в прототипе для цветовой индикации (`prototype/backend/routes/analytics.js`,
`posSummary`) — иллюстративное значение выбранное при реализации, не подтвержденный Product Manager
норматив.** Не зафиксирован ни в одном источнике Confluence из дерева задачи. Как и пороги утилизации
POS/SCO выше, должен быть настраиваемым параметром (SCR-08), а не жестко заданным числом.

### 9. Скорость обслуживания (среднее время чека, добавлено 2026-07-22)

Отдельная метрика от p95 длительности покупки (`requirements/02-system/entities-and-data-dictionary.md`,
раздел «Производительность кассы», где обе величины уже перечислены — «P95 длительности покупки» и
«Средняя длительность покупки» — но норматив/формула ранее не были зафиксированы отдельно от p95).
Используется на большой плашке ОД и на карточке магазина как «скорость обслуживания POS» /
«скорость обслуживания КСО»:

```
скорость обслуживания = среднее время чека (общая длительность покупки, усредненная по кассам типа POS/SCO)
```

В отличие от p95 (наихудший случай — 95-й процентиль), это типичная/среднестатистическая
длительность обслуживания. Норматив не зафиксирован в исходных документах Confluence — требует
подтверждения Product Manager; в прототипе показывается без цветовой индикации отклонения (в отличие
от p95, где индикация уже нормирована — см. «Цветовая индикация отклонений» ниже).

### 10. Количество магазинов/POS/КСО (большая плашка ОД, добавлено 2026-07-22)

Три отдельных счетчика, источник — реестр кассового сервера (мастер-данные), не телеметрия — см.
уточнение в `requirements/06-system-scenarios/system-scenarios.md` («Ввод магазина/кассы в
эксплуатацию»). Касса остается в счете «количество POS»/«количество КСО», даже если телеметрия от
нее не поступает.

**Касса не в эксплуатации (подтверждено Product Manager, 2026-07-22).** Если телеметрия от кассы не
поступает дольше **30 дней**, касса считается фактически не в эксплуатации — во всех местах, где
отображается статус конкретной кассы (таблица касс магазина, диагностика), она помечается
приглушенным/серым индикатором с указанием числа дней без телеметрии (например, «Офлайн 38 дн.»)
вместо обычного статуса. Порог 30 дней и сам факт визуальной пометки — решение, принятое при
доработке прототипа, не зафиксировано в исходных документах Confluence — норматив требует
подтверждения Product Manager при переносе в production.

### 11. Количество аутсайдеров (большая плашка ОД, добавлено 2026-07-22)

Число и доля (%) магазинов-аутсайдеров (см. классификацию аутсайдера в
`requirements/07-scenarios/business-scenarios.md`, этап 3) в текущей области видимости роли
(сеть/регион/магазин).

### 12. Динамика показателей большой плашки ОД (добавлено 2026-07-22)

Для всех четырех показателей раздела 10-11 (количество магазинов/POS/КСО/аутсайдеров) динамика
считается как **выбранный период сравнивается с предыдущим периодом той же длины**: например, если
в календаре выбраны последние 7 дней — сравниваются последние 7 дней с предыдущими 7 днями; если
выбраны 30 дней — с предыдущими 30 днями. Тот же принцип уже применялся для тренда регионов на
дашборде сети (`requirements/02-system/user-roles-and-functional-blocks.md`) — здесь формализован
как общее правило для всех показателей плашки «Общая информация».

### 13. Потенциальная экономия (плашка ОД, группа «Прочее», добавлено 2026-07-22)

Оценка суммы, которую сеть может сэкономить, если перевести потенциальные чеки с POS на КСО, в
пересчете на стоимость рабочего времени кассира:

```
потенциальная экономия (магазин) = (среднее время чека POS, сек / 3600)
                                     × потенциал чеков перевода на КСО (шт/нед)
                                     × ставка часа кассира (руб/USD/EUR за час)

потенциал чеков перевода на КСО (шт/нед) = нагрузка POS (чек/нед магазина) × потенциал_SCO (%, см. раздел «5. Потенциал SCO») / 100
```

Считается отдельно по каждому магазину (своя средняя скорость обслуживания POS — см. «9. Скорость
обслуживания»), сумма по всем магазинам области видимости роли (сеть/регион) — итоговое значение
плашки. При клике доступна детализация по магазинам (столбчатая диаграмма), аналогично другим
плашкам группы (см. `ai-artifacts/07-prototype-report.md`).

**Настраиваемые параметры (SCR-08, экран настроек).** Ставка часа кассира и валюта расчета — сетевые
параметры, доступны только роли ОД (аналогично прочим сетевым нормативам, РД менять не может).
Валюта — код из ограниченного набора (RUB/USD/EUR); отображаемый символ/подпись валюты берутся из
ключей локализации (`currency.RUB`/`currency.USD`/`currency.EUR`), а не жестко заданы в коде экрана —
чтобы смена валюты в настройках сразу отражалась в сумме экономии без переноса продукта на другую
локаль.

**Не подтверждено Product Manager.** Дефолтное значение ставки часа кассира (350 ₽/ч) и дефолтная
валюта (RUB) — иллюстративные значения, выбранные для прототипа, а не подтвержденный норматив.
Формула перевода «потенциал_SCO (%) × нагрузка POS (чек/нед)» в «потенциал чеков перевода на КСО
(шт)» — собственная интерпретация для прототипа (нигде явно не описана в исходных документах
Confluence); при переносе в production также требует подтверждения Product Manager.

### 14. Рейтинг региона/магазина (плашки ОД/РД, добавлено 2026-07-22)

Плашка «Рейтинг региона» (дашборд РД, группа «Прочее») и «Рейтинг магазина» (карточка магазина,
группа «Прочее») показывают три вертикальные строки — лидер, текущее место, «догоняющий»:

```
балл сущности (регион/магазин) = (доступность КСО, % + утилизация касс (POS+SCO вместе), % + доля чеков КСО, %) / 3
```

Рейтинг — сортировка по убыванию балла среди сопоставимых сущностей: для региона — среди ВСЕХ
регионов сети (не только своего, даже для роли РД — иначе рейтинг был бы бессмысленным); для
магазина — среди магазинов ТОГО ЖЕ региона (не сети целиком). «Лидер» — сущность с рангом №1;
«вы» — своя позиция; «догоняющий» — сущность на одну позицию ниже вас в рейтинге (ближайший
претендент на ваше место); если вы уже последние — строка «догоняющий» не показывается, если вы
уже лидер — строка «лидер» и «вы» объединяются в одну. Клик по плашке открывает полный
отсортированный список (все регионы сети / все магазины региона).

**Не подтверждено Product Manager.** Сама формула балла (равновзвешенное среднее трех процентных
показателей) и определение «утилизации» как усредненной по POS+SCO вместе (в отличие от отдельных
плашек «утилизация POS»/«утилизация SCO» в остальном интерфейсе) — собственная интерпретация для
прототипа; ни формула, ни веса показателей нигде не зафиксированы в исходных документах Confluence.

### 15. График потоков по часам и порог перегрузки (карточка магазина, добавлено 2026-07-22)

Плашка «Потоки по часам» (перед таблицей «Кассы магазина») показывает распределение чеков POS+КСО
по часам работы магазина (часы работы — `stores.opening_hour`/`stores.closing_hour`, см.
entities-and-data-dictionary.md) в виде сложенной столбчатой диаграммы (POS снизу, КСО сверху) с
линией тренда (скользящее среднее) и порогом перегрузки:

```
норматив чеков в час (магазин) = (норматив нагрузки POS, чек/нед + норматив нагрузки SCO, чек/нед) / 7 / часы работы в день
порог перегрузки (в час) = 0.7 × норматив чеков в час
```

Если выбран один конкретный день в календаре периода — на графике фактические чеки этого дня; если
период длиннее (неделя/месяц/произвольный диапазон) — среднее по каждому часу дня за весь период.
Под графиком — список часов, где фактическая нагрузка (POS+КСО вместе) превысила порог перегрузки,
для верхнеуровневого вывода о пиковых часах.

**Не подтверждено Product Manager.** Порог 70% и сама формула часового норматива (деление
существующих СЕТЕВЫХ недельных нормативов POS/SCO на 7 дней и на часы работы конкретного магазина,
без разбивки по кассам) — интерпретация для прототипа, отдельного часового или подушевого
(на кассу) норматива в исходных документах Confluence нет. Часы работы магазина по умолчанию
(гипермаркет 7–23, супермаркет 8–22, магазин у дома 8–23) — иллюстративные значения по формату
магазина, не подтвержденный норматив.

## Пороговые значения утилизации POS/SCO — настраиваемый параметр (уточнено Product Manager, 2026-07-21)

Значения ниже (1800/2000/2500/1500 чеков/нед) — это **иллюстративный пример из кейса** «Магазин №404» (`requirements/07-scenarios/business-scenarios.md`), а не фиксированное бизнес-правило, зашитое в продукт. Пороги нагрузки POS/SCO должны быть **настраиваемым параметром**, а не явным жестко заданным значением в коде отчетов. Все подобные настраиваемые параметры (нормативы p95/median, пороги утилизации POS/SCO и т.п.) должны быть вынесены в отдельное приложение/раздел настроек, а не быть частью логики самих аналитических дашбордов — см. `requirements/02-system/user-roles-and-functional-blocks.md` (раздел «Права доступа по ролям», экран настроек) и `ai-artifacts/02-screen.model.json` (SCR-08).

Пример из кейса (иллюстрация, не норматив):

- SCO: пример норматива нагрузки — 1800 чеков/нед. Если факт < норматива — индикатор «недогружены» (синий).
- POS: пример норматива нагрузки — 2000 чеков/нед. Если факт > верхнего порога — «перегруз» (риск очередей); если факт < нижнего порога — «избыток персонала». Конкретные числа верхнего/нижнего порога — тоже настраиваемые параметры, а не фиксированные 2500/1500.

## Цветовая индикация отклонений

- Производительность касс (p95, отклонение от норматива): до 15% — зеленый; 16–70% — желтый; ≥70% — красный.
- Доступность SCO (KPI-плашки): до 15% — красный; 16–70% — желтый; ≥70% — зеленый.

Примечание: направление шкалы цветов различается между блоками «Производительность» (рост отклонения — хуже) и «Доступность» (рост показателя — лучше); при реализации использовать логику соответствующего блока, а не единый обратный порог.

Плашки «Информация КСО»/«Информация POS» (список причин простоя ниже) с 2026-07-22 дополнительно
показывают в заголовке суммарное время простоя за выбранный период (сумма часов по всем
перечисленным причинам) — вместо только относительной длины полос по каждой причине.

## Технический фактор недоступности (примеры аномалий и решений)

**SCO:**
- **Нет бумаги** — простой выше медианы по сети → работа с дисциплиной персонала.
- **Ошибка банка** — простой выше медианы по сети → заявка в ИТ-отдел/банк-эквайер.
- **Заблокировано сотрудником** — простой выше медианы по сети → работа с дисциплиной персонала.
- Другие технические причины — см. ссылку в исходном документе Confluence (страница 5715099678, за пределами дерева данной задачи — не загружена в этот файл, см. `NEEDS_INPUT` ниже).

**POS (добавлено в прототипе при доработке блока POS, требует подтверждения Product Manager):**
явное указание Product Manager — «нет такого понятия как технический перерыв кассира» — кадровые/операционные
причины (отсутствие кассира на месте и т.п.) исключены из технических причин POS, оставлены только
технические сбои: **ошибка ККТ**, **сбой терминала эквайринга**, **ошибка сканера POS**. Список — рабочая
гипотеза прототипа для заполнения того же пробела, что и `NEEDS_INPUT` ниже (страница 5715099678 не
загружена), не подтвержденный Product Manager исчерпывающий перечень.

## Бизнес-фактор (эффективность и нагрузка)

- **Проверка доступности КСО** — аномалия при доступности ниже медианы по сети → работа с дисциплиной персонала.
- **Проверка утилизации ресурсов** — нагрузка SCO/POS относительно нормативов (см. пороги выше).
