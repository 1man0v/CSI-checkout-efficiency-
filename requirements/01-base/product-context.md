# Контекст и границы продукта

Источник: Confluence, «Продуктовое решение: Эффективность магазина» (space SCO, page 6318325801) и вложенные страницы.

## Проблема

В экосистеме Set Retail отсутствует единый инструмент комплексного анализа эффективности зоны расчета магазина, объединяющий классические кассы (POS/Touch), кассы самообслуживания (SCO/Hybrid), доступность оборудования, нагрузку персонала и реальную пропускную способность.

Существующие инструменты покрывают только отдельные параметры (количество чеков, продажи, общая информация в чеке), но не дают единой модели, позволяющей:

- понимать реальные причины очередей;
- выявлять магазины-аутсайдеры;
- оценивать эффективность использования SCO;
- выявлять скрытые потери из-за недоступности касс;
- определять избыточную или недостаточную нагрузку на персонал;
- сравнивать эффективность магазинов между собой;
- выявлять потери потенциальной доли SCO;
- анализировать технические и бизнес-факторы в одной системе.

Отдельная проблема — отсутствие прозрачной аналитики по реальной доступности КСО. Касса формально может считаться «включенной», но фактически быть недоступной для покупателя: нет бумаги, касса заблокирована сотрудником, не открыта смена, неисправен сканер/весы, не работает эквайринг, касса физически перекрыта товаром и т.д.

Последствия текущего состояния:

- репутационные риски CSI;
- снижение пропускной способности магазинов;
- рост очередей;
- потеря потенциальной выручки;
- снижение доли SCO;
- избыточные затраты на персонал;
- отсутствие прозрачности операционных проблем.

## Текущая реализация (as-is)

Аналитика в Set Retail 10 сегодня ограничена: транспортом событий в Kafka/Prisma, отдельными техническими метриками, локальными Grafana-дашбордами, ручными Excel-отчетами. Отсутствует сквозная аналитика POS/SCO, оценка «потенциала SCO», анализ реальной утилизации касс, автоматическое выявление аутсайдеров, оценка скрытой недоступности КСО, аналитика очередей и автоматические рекомендации для бизнеса. Также нет единого механизма сбора телеметрии, агрегации метрик, расчета нормативов, сравнения магазинов и визуализации отчетов в Set Centrum.

## Предлагаемое решение

Модуль Set: система мониторинга и аналитики эффективности зоны расчета магазина. Модуль обеспечивает: сбор телеметрии с POS/SCO, анализ производительности касс, анализ доступности оборудования, оценку утилизации ресурсов, анализ потоков покупателей, выявление потерь эффективности, поиск причин очередей, анализ «потенциала SCO», прогнозирование нагрузки (MVP2), автоматические рекомендации и задания.

Аналитический стек: DWH, Kafka, ClickHouse, Apache Superset, встроенные дашборды в Set Centrum. Подробности — см. `requirements/03-architecture/technical-constraints.md`.

## Бизнес-цели

- **Повышение эффективности зоны расчета** — рост пропускной способности магазинов и снижение времени ожидания покупателей.
- **Рост доли покупок через SCO** — выявление магазинов и сценариев для перенаправления покупателей с POS на SCO.
- **Контроль доступности оборудования** — прозрачный контроль реальной доступности касс и оборудования.
- **Снижение потерь продаж** — минимизация потерь оборота из-за недоступности касс, ошибок оборудования и неправильной организации зоны расчета.
- **Оптимизация затрат на персонал** — выявление избыточно открытых POS, недогруженных SCO, неоптимальных графиков и неэффективного распределения покупателей.
- **Выявление магазинов-аутсайдеров** — автоматическое определение магазинов, отклоняющихся от нормативов сети по доступности, доле SCO, производительности, нагрузке, uptime оборудования и эффективности использования ресурсов.
- **Единая система операционной аналитики** — общий аналитический контур для операционного директора, регионального директора, директора магазина, технических служб, службы поддержки и продуктовых команд.

### Целевой KPI (пример из документа кейса MVP)

| KPI | Цель |
| --- | --- |
| Доля чеков SCO | Рост с 20% до 28% |
| Доступность SCO | > 90% |
| Утилизация SCO | Рост по сети |
| Количество магазинов-аутсайдеров | Снижение |
| Потенциальные чеки SCO | Снижение объема чеков на POS |

## Целевая аудитория / роли

- Операционный директор — здоровье всей сети, выполнение годового KPI по доле чеков КСО, минимизация упущенного оборота, оптимизация затрат на персонал.
- Региональный директор — KPI региона, выравнивание магазинов-аутсайдеров, оптимизация штатного расписания и загрузки POS/SCO.
- Директор магазина — оперативное управление зоной расчета, контроль доступности касс, управление очередями.
- Технические службы, служба поддержки, продуктовые команды — подтверждены Product Manager как отдельные пользовательские роли системы (не просто адресаты отчетов без доступа); их функции описаны в `requirements/02-system/user-roles-and-functional-blocks.md`.

Подробные роли, их права и сценарии — см. `requirements/02-system/user-roles-and-functional-blocks.md` и `requirements/07-scenarios/business-scenarios.md`.

## Границы продукта (MVP1 / MVP2)

**MVP1** (объем текущего релиза):

- сбор телеметрии с POS/SCO;
- расчет основных операционных метрик;
- базовый дашборд по сети (Executive View);
- базовый дашборд по магазину (Store View);
- дашборд анализа доступности SCO;
- дашборд анализа производительности POS/SCO;
- дашборд анализа потенциала SCO;
- ручная простановка нормативов (p95, median);
- отчеты в Apache Superset;
- встройка отчетов в Set Centrum;
- таблица аутсайдеров;
- отправка агрегированных данных телеметрии через ЦСЛ.

**MVP2** (не входит в текущий объем, зафиксировано как будущий этап):

- прогнозирование нагрузки YoY/MoM;
- автоматическое выявление аномалий;
- работа с нормативами;
- работа с причинами деградации;
- сравнение магазинов-аналогов;
- heatmap использования SCO;
- аналитика для торговых сетей (внешним клиентам).

Также как отдельная, архитектурно независимая надстройка описана концепция операционного ИИ-консультанта Set Retail Pro (интеллектуальный слой над аналитической платформой, отвечающий на вопросы на естественном языке на основе готовых аналитических модулей). Это не часть MVP1/MVP2 в исходном документе, а самостоятельное продуктовое предложение — см. `requirements/02-system/ai-advisor-concept.md`.

## Известные ограничения / риски

- **Качество данных** — корректность аналитики напрямую зависит от полноты телеметрии и стабильности передачи событий с касс.
- **Нагрузка на инфраструктуру** — хранение и обработка большого объема данных от POS/SCO в режиме, близком к реальному времени.
- **Сложность внедрения** — требуются доработки по отправке телеметрии на кассах, настройка POSDWH, настройка ClickHouse, интеграция Superset, настройка дашбордов.
- **Интерпретация аналитики** — часть данных требует верификации бизнесом и операционными службами (например, недогруз кассы может быть связан с расположением, низкая доля SCO — с аудиторией магазина, очереди — с логистикой торгового зала).

## Дополнительные материалы (иллюстративные, не часть формальных требований)

- Интерактивный кликабельный прототип «Эффективность зоны расчета» (Confluence page 6487408709) — демонстрирует UX и логику рекомендаций на синтетических данных, не подключен к реальной аналитике.
- Дизайн-система «Set · Эффективность» (Confluence page 6487081052) — токены, компоненты и UI-кит для 4 экранов прототипа; статус «Черновик», требует ревью перед продакшн-использованием, не является наследованием существующего бренда Set/Crystals.

## Принцип формирования цены (подтверждено Product Manager, 2026-07-20)

Цена объекта продажи зависит от атрибута продукта — количества касс (POS+SCO), подключенных к аналитическому модулю (не фиксированная цена). Обоснование: все метрики в требованиях считаются «на кассу»/«на магазин», поэтому цена по количеству касс соответствует модели ценности продукта (чем больше касс под мониторингом, тем больше пользы) и уже подтвержденной on-premise-модели развертывания (см. `requirements/03-architecture/technical-constraints.md`).

## Тип объекта продажи и периодичность оплаты (подтверждено Product Manager, 2026-07-20)

- Тип объекта продажи: лицензия.
- Периодичность оплаты: подписка (регулярный периодический платеж; точная частота — ежемесячно/ежегодно — не уточнялась и не является блокером для модели продукта).
- Поддержка включена в подписку — отдельным объектом продажи (`service`) не оформляется.
- Принцип формирования цены: по количеству касс (POS+SCO), см. выше.

Итоговый объект продажи: **Лицензия на аналитический модуль по подписке, с ценой за количество подключенных касс, включая поддержку.**
