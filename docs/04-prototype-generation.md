# 04. Создание прототипа

## Работа с NEEDS_INPUT

Перед запуском этапа ИИ рекурсивно проверяет все файлы в `requirements/`. Если незакрытый `NEEDS_INPUT` влияет на результат этапа, ИИ не принимает решение самостоятельно: формирует вопросы в `ai-artifacts/needs-input.md`, задает их Product Manager или клиенту и останавливает этап. После ответа ИИ обновляет исходный файл требований, а Product Manager подтверждает изменение. Только затем этап продолжается.


## Цель этапа

На этом этапе утвержденный визуальный прототип превращается в работающий прототип с frontend, backend, API и базой данных.

Прототип должен позволять пройти ключевые пользовательские сценарии не только визуально, но и функционально: сохранять и читать данные, применять основные бизнес-правила и при необходимости использовать безопасные тестовые интеграции.

Прототип можно показать клиенту и использовать для проверки продукта на реалистичных, демонстрационных либо явно согласованных клиентских данных.

Прототип не является production-системой. Его код не передается в эксплуатацию как финальный код и не заменяет инженерную реализацию через GitHub Spec Kit.

Результат этапа:

```text
Approved Prototype
```

## Что выполняется на этапе

Инструмент должен:

1. Использовать утвержденный визуальный прототип как визуальный и сценарный источник истины.
2. Создать отдельное приложение прототипа.
3. Реализовать frontend, backend, API и базу данных в объеме, необходимом для проверки ключевых сценариев.
4. Добавить воспроизводимую схему базы данных и безопасные демонстрационные данные.
5. Реализовать основные бизнес-правила из Product Model.
6. Подключать только безопасные тестовые интеграции либо контролируемые заглушки.
7. Описать запуск, сброс данных и ограничения.
8. Проверить работу ключевых сценариев от интерфейса до базы данных.
9. Зафиксировать упрощения, которые нельзя переносить в production.
10. Проверить соответствие прототипа требованиям, модели экранов и визуальному прототипу.

## Ограничения

На этапе нельзя:

- заявлять production-ready статус;
- считать архитектуру прототипа финальной архитектурой продукта;
- использовать секреты и реальные персональные данные без явного согласования;
- подменять прототипом инженерную реализацию;
- создавать production-систему, которая должна разрабатываться через GitHub Spec Kit и Feature SDD.

---

## Критерии готовности

- frontend, backend, API и база данных запускаются;
- схема и демонстрационные данные воспроизводимы;
- ключевые сценарии работают end-to-end;
- данные сохраняются и корректно отображаются;
- интерфейс соответствует утвержденному визуальному прототипу;
- бизнес-правила соответствуют Product Model;
- ограничения по безопасности и данным документированы;
- демонстрация не требует скрытых ручных действий;
- итоговый статус — `READY_FOR_CLIENT_DEMO` или `BLOCKED_FOR_CLIENT_DEMO`.

После утверждения прототипа формируется карта функций. Если после демонстрации требуется изменение, Product Manager самостоятельно перезапускает процесс с нужного этапа.
