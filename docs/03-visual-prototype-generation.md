# 03. Создание визуального прототипа

## Работа с NEEDS_INPUT

Перед запуском этапа ИИ рекурсивно проверяет все файлы в `requirements/`. Если незакрытый `NEEDS_INPUT` влияет на результат этапа, ИИ не принимает решение самостоятельно: формирует вопросы в `ai-artifacts/needs-input.md`, задает их Product Manager или клиенту и останавливает этап. После ответа ИИ обновляет исходный файл требований, а Product Manager подтверждает изменение. Только затем этап продолжается.


## Цель этапа

На этом этапе утвержденная модель экранов превращается в кликабельный визуальный прототип.

Визуальный прототип — это HTML-интерфейс без настоящего backend, базы данных и реальных интеграций. В нем должны работать навигация, переходы, вкладки, формы, фильтры, диалоги, выдвижные панели и основные состояния экранов. Для демонстрации используются встроенные тестовые данные и локальная логика.

Результат этапа:

```text
Approved Visual Prototype
```

Визуальный прототип нужен, чтобы Product Manager мог проверить структуру интерфейса, пользовательские сценарии и визуальные решения до создания функционального прототипа с API и базой данных.

## Входные данные

```text
ai-artifacts/01-product.model.json
ai-artifacts/02-screen.model.json
requirements/
```

Дополнительно пользователь может передать:

- Figma-файл или ссылку на Figma;
- UI kit или дизайн-систему;
- существующие компоненты и макеты;
- визуальные референсы;
- фирменные стили и правила оформления.

### Использование Figma

Figma используется по желанию пользователя. Пользователь должен явно указать в запросе, нужно ли использовать Figma и в каком режиме.

Figma можно использовать:

- на чтение — как источник существующих компонентов, стилей, макетов и правил дизайн-системы;
- для генерации новых макетов и компонентов, если это требуется для визуального прототипа;
- для последующей ручной корректировки макетов Product Manager или дизайнером.

Git остается основным хранилищем артефактов Product Compiler. Если визуальный прототип создается или дорабатывается в Figma, в Git необходимо сохранить ссылку на файл, описание использованных компонентов и экспортируемую либо воспроизводимую версию результата.

## Что выполняется на этапе

Инструмент должен:

1. Прочитать Product Model и Screen Model.
2. Проверить, что для ключевых сценариев определены необходимые экраны и переходы.
3. Создать визуальную структуру каждого экрана.
4. Реализовать кликабельную навигацию и локальные взаимодействия.
5. Показать основные состояния: loading, empty, success, validation error и server error, если они предусмотрены моделью экранов.
6. Использовать тестовые данные и заглушки без настоящего API и базы данных.
7. При заданном пользователем режиме использовать Figma для чтения существующих компонентов либо для генерации новых макетов и компонентов.
8. Создать машиночитаемую модель визуального прототипа.
9. Подготовить отчет о соответствии модели экранов.

Если при создании визуального прототипа обнаружено, что модель экранов неполна или противоречива, инструмент не должен молча исправлять ее. Нужно зафиксировать проблему и вернуть статус:

```text
BLOCKED_FOR_VISUAL_PROTOTYPE
```

После исправления Product Manager самостоятельно перезапускает процесс с этапа 02 или другого нужного этапа.

## Критерии готовности

- ключевые сценарии можно пройти кликами;
- экраны и переходы соответствуют Screen Model;
- интерфейс не зависит от настоящего API или базы данных;
- основные состояния интерфейса представлены;
- тестовые данные не выдаются за реальные;
- использование Figma и источники компонентов задокументированы, если Figma применялась;
- выявленные проблемы Screen Model не скрыты;
- итоговый статус — `APPROVED_VISUAL_PROTOTYPE` или `BLOCKED_FOR_VISUAL_PROTOTYPE`.

После утверждения визуального прототипа выполняется этап:

```text
docs/04-prototype-generation.md
```
